## Locked requirements preserved

The logical EvidenceSnapshot fields, output-only commitment, integer paise, epoch-day dates, epoch-second timestamps, binary flags, 36 completed UTC income/month-activity buckets and 156 completed ISO weeks in oldest-to-newest order are locked. Four-child Poseidon trees, in-preimage domain separation, zero padding, real TypeScript/Circom parity, authenticated FIP signature/consent/owner prerequisites, historical cutoff/directory reconstruction and no persistent plaintext snapshots are locked. Exact tags, byte serialization, field mappings, monetary bit bounds, history formula and signed-policy/public-signal encodings remain review decisions. Authority: Decision Register and existing Poseidon/authorization reviews, not this proposal.

## Proposed interface and decisions

| Boundary | Proposed 0.1.0 convention / decision required |
|---|---|
| Snapshot-to-hash API | Exact seven scalar keys: `passportId, holderBinding, evidenceProviderId, evidenceDataHash, verifiedHistoryStartDate, evidenceUpdatedAt, sourceDirectoryVersion`; plus the three locked arrays. In-memory `bigint`; JSON canonical unsigned decimal strings; reject numeric JSON, negatives, leading zeros and overflow rather than silently reducing. The prototype implements this isolated boundary only. Agree the transport/schema version before moving it to `shared/`. |
| Poseidon profile | Candidate tags: income `[1100,1101,1102]`, weekly `[1200,1201,1202,1203]`, monthly `[1300,1301,1302]`; metadata `[1400,1499]`. Candidate metadata order is the seven scalars above followed by income/weekly/monthly roots, forming `10->3->1`. Missing children are zero at every level. Real parity is demonstrated; constants/order still need approval as one versioned manifest. |
| Dataset bytes / evidenceDataHash | Resolve the runtime/proposal mismatch before integration: runtime hashes `{accountOwnerBinding,transactions}` while the proposal serializes `{accountOwner,timeBounds,transactions,version}`. Recommend one explicit versioned UTF-8 serializer with fixed key order; normalize first, then sort by integer timestamp and normalized transaction ID with a specified bytewise comparator (no locale dependence), reject duplicate normalized IDs. Agree exact account-owner fields, dataset range semantics and every authenticated source/currency field relevant to normalization/classification. Exclude consent IDs, signatures and fetch entropy as locked. No serializer is adopted here. |
| Digest/provider/holder mappings | Candidate from existing review/A proposal: full SHA-256 bytes interpreted big-endian, `% r` only at this named digest-to-field boundary; provider = SHA-256 of `UTF8("GIGVAULT_PROVIDER_ID_V1|") || UTF8(canonicalProviderId)` then `% r`; holder = big-endian EVM-address `uint160`, distinct from stable identity. Require exact provider ASCII/case rules and digest vectors from A. Existing string IDs/hex hashes/JS numbers must be adapted explicitly; this prototype uses fixed synthetic field literals instead. |
| Amount/range safety | Candidate monthly totals and average thresholds: unsigned 64-bit paise; reject unsafe source numbers before aggregation, use BigInt end-to-end. For at most 36 months, sum and `threshold*N` are below `2^70`; constrain operands/windows and both comparison sides to the agreed widths. Approve maximums and overflow behavior with A before predicate circuits. A boundary hash fixture is not a range proof. |
| Completed buckets/history | Keep fixed evidence cutoff and historical directory version. Recommend half-open UTC month/Monday-week intervals, with boundary/leap-day vectors from A. History is a separate rule: candidate pass when first recognized payout date is at/before cutoff date minus requested calendar months, clamping day to that target month's last day. A currently uses epoch-day `0` when no history exists; propose explicit `0 = absent` and fail enabled history for it, never treating it as Jan 1970 tenure. Sentinel/date-domain and anniversary/clamp semantics need approval before implementation. |
| Signed policy / approval / signals | Use the authorization review's candidate EIP-712 policy plus separate current-holder approval. Both owners/frontend must agree exact type strings, widths, domain, disabled-zero fields, expiry and intended consumer/signer checks. For arbitrary request/policy/domain `bytes32`, recommend two ordered 128-bit limbs (high then low), each range-constrained, preserving the full signed value rather than accidental truncation/modulo. This is a new proposal, not a frozen manifest. |

Proposed later proof manifest must bind the locked passport ID, current evidence version/commitment, request ID, verifier ID, signed policy hash and deployment domain; canonical enabled criteria/windows/thresholds, expiry/freshness context; and actual constrained income/history/activity PASS/FAIL outputs. Exact ordering, limb representation and relation between signed policy bytes and public criterion fields must be reviewed together. Signatures, current ACTIVE passport/holder/version, freshness and exact intended consumer policy remain independently checked outside Circom; mathematical verification alone authorizes no action. The lab's four root outputs and `expectedCommitment` input are diagnostic only and are not this application manifest.

## Handoff and approval gate

Backend B provides the isolated adapter/circuits, real synthetic vectors and a reproducible test harness. Backend A should independently reproduce these hash vectors, provide one approved authenticated-data byte/digest vector with provider/holder mappings, and calendar/amount/no-history boundary cases. Together resolve the table and publish one versioned shared manifest; changed tags/order/encoding require a new version. Only then move/import the adapter into shared ownership, test fresh-consent reconstruction, implement range-safe predicates and signed-policy binding, and eventually generate deployable setup/verifier artifacts.

Current evidence: **22 interoperability tests passed**, 15 snapshots matched all roots/commitment, real R1CS witness/tampering checks passed, and a real local H5 Groth16 proof verified while a changed public hash failed. This proves pinned-library hash/proving compatibility, not authenticated dataset normalization, financial conditions, authorization or consumer security. Passport lifecycle remains separately tested. No financial consumer implementation or deployment is part of this milestone.
